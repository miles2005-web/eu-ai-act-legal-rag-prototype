# EU AI Governance Assessment Platform v2.0 — Implementation Plan

## 1. Purpose and design constraints

This plan upgrades the current chat-based EU AI Act RAG prototype into a structured assessment workflow. The target is a demonstrable legal-engineering prototype suitable for an academic portfolio and for showing how a real compliance assessment could be conducted, reviewed, and reproduced.

The v2.0 prototype should demonstrate five ideas clearly:

1. A user creates and can later reopen an assessment case.
2. A dynamic questionnaire converts user answers into validated, structured facts.
3. Versioned, deterministic rules produce traceable legal findings.
4. The existing RAG corpus supplies legal evidence and explanations, but does not make the legal classification itself.
5. The system produces a standardized assessment report with conclusions, assumptions, missing facts, and citations.

The intended architecture is a modular monolith: one Python application, one Streamlit frontend, one small transactional database, and the existing legal retrieval store behind a service interface. A separate API service, distributed components, enterprise identity management, and multi-tenant infrastructure are not required for this version.

The controlling design principle is:

> Rules decide; RAG supports; the LLM explains.

## 2. MVP scope

### 2.1 Included in the MVP

The MVP is limited to preliminary classification under Regulation (EU) 2024/1689 (the EU AI Act). It should assess:

- whether the described system is potentially an AI system for purposes of the assessment;
- whether the case appears to fall within the territorial and material scope of the EU AI Act;
- whether an exclusion or special scope condition may apply;
- which supply-chain roles the organization may hold:
  - provider;
  - deployer;
  - importer;
  - distributor;
- whether the facts indicate a potentially prohibited AI practice under Article 5;
- whether the system may be high-risk under:
  - Article 6(1) together with Annex I;
  - Article 6(2) together with Annex III;
  - the Article 6(3) exceptions and profiling override;
- a preliminary mapping of core obligations based on the identified role and classification;
- unresolved factual questions and findings requiring legal review;
- a standardized Markdown assessment report supported by retrieved EU AI Act provisions.

The system must allow more than one role to apply. It must also distinguish a definitive negative result from an unresolved result caused by missing facts.

### 2.2 Explicitly outside the MVP

The following are deferred:

- substantive GDPR, Data Act, Cyber Resilience Act, product-liability, or sector-specific assessments;
- complete GPAI and systemic-risk model obligations;
- conformity-assessment workflow management;
- document upload and automated extraction of facts from contracts or technical files;
- collaborative review, comments, approvals, enterprise access control, and organization tenancy;
- production-grade PDF generation and electronic signatures;
- a general-purpose no-code legal rule editor;
- automatic legal conclusions generated by an LLM;
- migration of historical chats, because the current application does not persist them as assessment cases.

The report may contain a clearly labelled “possible cross-regulatory follow-up” note when facts mention personal data or connected products, but v2.0 must not present this as a GDPR or Data Act determination.

### 2.3 MVP completion criteria

The MVP is complete when a user can create a case, answer a branching questionnaire, save and reopen it, run the assessment, inspect the rule trace and supporting provisions, and export a reproducible Markdown report. At least four reference scenarios should be demonstrated end to end:

- recruitment candidate screening;
- a medical-device safety component;
- a low-risk customer-service assistant;
- a scenario that potentially triggers Article 5 and requires legal review.

## 3. Proposed v2.0 application shape

```text

    -> Case service
        -> Questionnaire engine -> validated facts -> case database
        -> Assessment orchestrator
            -> deterministic rule engine -> findings + missing facts
            -> legal evidence service -> existing RAG store
            -> report builder -> versioned report
    -> case-aware explanation assistant (secondary feature)
```

## 4. Assessment fact schema

### 4.1 Schema principles

The fact schema is the stable contract between the questionnaire, rules, database, and report. UI labels and question ordering may change without changing fact paths.

Each fact should:

- have a defined type and a stable path;
- allow `unknown` where the user cannot answer safely;
- record its source and last update time;
- avoid embedding a legal conclusion in the question;
- distinguish user assertions from rule-engine findings;
- be snapshot when an assessment run starts.

Boolean legal facts should normally use `yes | no | unknown`, not a database boolean, so that unanswered facts are not silently treated as false.

### 4.2 Top-level schema

```json
{
  "schema_version": "2.0.0",
  "case": {},
  "system": {},
  "scope": {},
  "organisation": {},
  "supply_chain": {},
  "use_context": {},
  "practices": {},
  "high_risk": {},
  "fact_metadata": {}
}
```

## 5. Finding model

### 5.1 Purpose

A finding is a structured result from one rule or a coordinated group of rules. It is not an LLM answer and should be serializable, testable, and suitable for direct report generation.

### 5.2 Finding statuses

Use the following statuses consistently:

- `applies`: the available facts satisfy the rule;
- `does_not_apply`: the available facts are sufficient to reject the rule;
- `potentially_applies`: the facts indicate a material trigger, but an exception or legal review remains;
- `undetermined`: required facts are missing or unknown;
- `not_assessed`: the topic is outside the current run or blocked by an earlier gate.

Do not assign numerical “legal confidence” in the MVP. The status, missing facts, and review flag communicate uncertainty more honestly.

### 5.3 Proposed model

```json
{
  "finding_id": "uuid",
  "assessment_run_id": "uuid",
  "category": "high_risk",
  "issue_code": "AIA_HIGH_RISK_ANNEX_III_EMPLOYMENT",
  "status": "applies",
  "title": "Employment candidate screening is listed in Annex III",
  "summary": "The described intended purpose matches the listed employment use case.",
  "rule_id": "AIA-HR-ANNEX-III-4A",
  "rule_version": "2.0.0",
  "fact_refs": [
    "use_context.domain",
    "use_context.task"
  ],
  "missing_fact_refs": [],
  "reason_codes": ["EMPLOYMENT", "CANDIDATE_SELECTION"],
  "legal_basis": [
    {
      "instrument": "EU_AI_ACT",
      "citation": "Article 6(2)",
      "anchor": "article:6:paragraph:2"
    },
    {
      "instrument": "EU_AI_ACT",
      "citation": "Annex III, point 4(a)",
      "anchor": "annex:III:point:4a"
    }
  ],
  "evidence_refs": ["vector-chunk-id"],
  "requires_legal_review": false,
  "trace": []
}
```

### 5.4 Finding categories

The MVP should support:

- `ai_system_status`;
- `scope`;
- `role_provider`;
- `role_deployer`;
- `role_importer`;
- `role_distributor`;
- `prohibited_practice`;
- `high_risk_article_6_1`;
- `high_risk_article_6_2`;
- `high_risk_article_6_3_exception`;
- `obligation_group`;
- `information_gap`.

Separate role findings are preferable to a single role enum because an organization may hold multiple roles.

## 6. Rule engine design

### 6.1 MVP implementation approach

Implement the rules as typed Python code with declarative metadata. Do not build a generic visual rule language for the prototype.

Each rule should expose:

```python
class AssessmentRule:
    rule_id: str
    version: str
    category: str
    required_facts: tuple[str, ...]
    legal_basis: tuple[LegalAnchor, ...]

    def evaluate(self, facts: AssessmentFacts) -> RuleResult:
        ...
```

Rules should be pure functions: the same fact snapshot and rule version must always return the same result. They must not access Streamlit state, call the LLM, query the vector store, or write to the database.

### 6.2 Evaluation phases

Run rules in this order:

1. **AI-system screening** — determine whether assessment can proceed or needs review.
2. **Scope** — evaluate EU connection and exclusions.
3. **Roles** — independently evaluate provider, deployer, importer, and distributor status.
4. **Prohibited practices** — run whenever scope potentially applies; do not wait for high-risk classification.
5. **High-risk Article 6(1)** — product/safety-component route.
6. **High-risk Article 6(2)** — Annex III route.
7. **Article 6(3)** — test exceptions and the profiling override.
8. **Obligation mapping** — derive a preliminary checklist from role and classification findings.

An `AssessmentOrchestrator` should invoke the phases, collect all findings, preserve their trace, and identify missing facts. It should not stop at the first positive role or risk finding.

### 6.3 Unknown propagation

Rules must distinguish three situations:

- a required fact is unknown: return `undetermined` and list it in `missing_fact_refs`;
- sufficient facts disprove the rule: return `does_not_apply`;
- a possible prohibition or exception depends on detailed legal interpretation: return `potentially_applies` with `requires_legal_review = true`.

This distinction is essential for a credible legal workflow and for generating the next questionnaire step.

### 6.4 Evidence enrichment

After deterministic evaluation, the evidence service should:

1. read each finding's legal anchors;
2. use metadata-filtered retrieval for the named Article or Annex;
3. attach the best authoritative chunks to `evidence_refs`;
4. save the retrieved text, citation, source, similarity score, and corpus version with the assessment run;
5. optionally ask the LLM to explain the already-determined result using only the finding and attached evidence.

If evidence retrieval fails, the finding remains visible but is marked as lacking retrieved support. A retrieval failure must never silently change a deterministic rule result.

### 6.5 Rule versioning and tests

Use one ruleset version string for each assessment run. Every rule must have tests covering:

- a positive scenario;
- a negative scenario;
- each material exception;
- missing or unknown facts;
- conflicting facts;
- the expected legal anchors and reason codes.

Reference scenario fixtures should contain a fact snapshot and expected findings. These fixtures will be more important than the current question-answer retrieval tests for v2.0.

## 7. Questionnaire flow

### 7.1 User journey

The questionnaire should be a guided case workflow rather than a chat transcript:

1. **Create case** — title, organization, system name, description.
2. **System characteristics** — intended purpose, outputs, autonomy, inference.
3. **EU scope** — establishment, market placement, putting into service, EU output use, exclusions.
4. **Supply-chain role** — development, branding, internal use, import, distribution, modifications.
5. **Potentially prohibited practices** — Article 5 factual screening.
6. **High-risk route** — Annex I product route, Annex III use-case route, Article 6(3) facts.
7. **Review facts** — show all normalized answers and unresolved questions.
8. **Run assessment** — create an immutable run snapshot and findings.
9. **Review results and report** — inspect conclusions, evidence, and information gaps.

### 7.2 Dynamic behavior

Questions should be defined in a versioned registry with:

```json
{
  "question_id": "HR-ANNEX-I-003",
  "fact_path": "high_risk.requires_third_party_conformity_assessment",
  "answer_type": "tri_state",
  "prompt": "Is the product required to undergo a third-party conformity assessment before market placement or putting into service?",
  "help_text": "Answer based on the product legislation applicable to the product, not on the AI Act alone.",
  "show_if": [
    ["high_risk.product_covered_by_annex_i", "equals", "yes"]
  ],
  "blocks_rules": ["AIA-HR-ARTICLE-6-1"],
  "legal_relevance": ["Article 6(1)(b)"]
}
```

Dynamic behavior should be deterministic:

- hide questions that cannot affect any reachable rule;
- show follow-up questions when a triggering answer is given;
- prioritize facts listed as missing by unresolved rules;
- always offer `I do not know` where appropriate;
- save each answer immediately or at the end of each section;
- rerun a lightweight assessment preview after a section is saved;
- show why a sensitive or technical question matters without suggesting the desired answer.

The LLM may explain a question in plain language, but it must not invent questionnaire branches or write directly to the fact store without user confirmation.

### 7.3 Streamlit pages

The minimum frontend is:

- **Cases** — create, reopen, rename, or archive a case;
- **Questionnaire** — section progress, dynamic questions, autosave;
- **Review** — normalized facts and missing answers;
- **Results** — finding cards grouped by scope, roles, prohibited practices, high-risk status, and obligations;
- **Evidence and report** — retrieved provisions, rule trace, and Markdown export;
- **Explain this assessment** — optional case-aware chat using existing findings and evidence.

Retrieval count and token budget should be removed from the primary user workflow. Those are implementation diagnostics, not compliance-assessment inputs.

## 8. Minimal database design

### 8.1 Technology choice

Use SQLite for the demonstrable prototype, with foreign keys enabled and a repository layer that keeps SQL out of Streamlit pages. SQLAlchemy 2.x is appropriate but not mandatory; direct `sqlite3` is acceptable if repository interfaces and migrations remain explicit.

The legal vector store remains separate. Chroma or `vector_store.json` must not be used as the case database.

### 8.2 Minimal tables

#### `assessment_cases`

| Column | Purpose |
|---|---|
| `id` | UUID/text primary key |
| `title` | Case name |
| `status` | `draft`, `ready`, `assessed`, `archived` |
| `schema_version` | Fact-schema version |
| `facts_json` | Current validated fact document |
| `created_at` | Creation timestamp |
| `updated_at` | Last modification timestamp |

#### `fact_events`

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `case_id` | Parent case |
| `fact_path` | Stable fact path |
| `old_value_json` | Previous value |
| `new_value_json` | New value |
| `source` | Questionnaire, case edit, or confirmed assistant suggestion |
| `question_id` | Originating question when relevant |
| `created_at` | Change timestamp |

#### `assessment_runs`

| Column | Purpose |
|---|---|
| `id` | Run ID |
| `case_id` | Parent case |
| `facts_snapshot_json` | Immutable facts used by the run |
| `ruleset_version` | Rule version |
| `questionnaire_version` | Questionnaire version |
| `corpus_version` | Evidence corpus/index version |
| `status` | `running`, `completed`, `failed` |
| `created_at` | Run timestamp |

#### `findings`

| Column | Purpose |
|---|---|
| `id` | Finding ID |
| `assessment_run_id` | Parent run |
| `category` | Finding category |
| `issue_code` | Stable issue code |
| `status` | Structured finding status |
| `rule_id` | Producing rule |
| `payload_json` | Full finding, trace, legal basis, and evidence references |

#### `reports`

| Column | Purpose |
|---|---|
| `id` | Report ID |
| `assessment_run_id` | Source run |
| `report_version` | Report-template version |
| `report_json` | Structured report data |
| `markdown_text` | Rendered report |
| `created_at` | Generation timestamp |

Five tables are sufficient for the MVP. Users, organizations, permissions, comments, and separate evidence tables can be added only when the prototype needs them.

### 8.3 Persistence behavior

- Editing a draft updates `assessment_cases.facts_json` and appends a `fact_events` row.
- Running an assessment creates a new `assessment_runs` snapshot; prior runs are never overwritten.
- Findings belong to one immutable run.
- Regenerating a report may create a new report version but does not rerun legal rules.
- Changing a fact marks the latest result as stale until a new run is created.

## 9. Migration strategy from the current RAG application

The migration should be incremental and keep the existing chat demo available until the v2 workflow is complete.

### Step 1: Freeze and characterize the current baseline

- Preserve `app_chroma.py` as the legacy demo during development.
- Record the current corpus size, embedding model, and retrieval behavior.
- Repair or replace the current golden-query path mismatch and capture baseline retrieval fixtures.
- Do not rebuild embeddings merely to begin v2 development.

### Step 2: Extract a reusable evidence adapter

- Move JSON loading, cosine search, metadata filtering, reference extraction, and token budgeting behind a `LegalRetriever` interface.
- Keep the first adapter compatible with the existing `vector_store.json`.
- Return typed evidence objects instead of Markdown strings.
- Keep LLM prompting outside the retriever.

This step should preserve current retrieval results while removing retrieval logic from the UI.

### Step 3: Add the v2 domain alongside the legacy app

- Introduce fact, finding, case, and assessment-run models.
- Add SQLite repositories and migrations.
- Add deterministic rules and fixtures without connecting them to the old chat history.
- Add a separate v2 Streamlit entry point or multipage navigation while retaining the legacy app as a fallback.

### Step 4: Connect findings to RAG evidence

- Convert each rule's legal basis into structured retrieval filters.
- Retrieve the relevant EU AI Act provisions after rule evaluation.
- Save evidence references and the corpus version with the run.
- Use the LLM only for optional explanations based on the fixed finding and retrieved evidence.

### Step 5: Improve the corpus pipeline after the workflow works

- Retain more metadata currently produced by the legal chunker, including paragraph, point, chapter, and section fields.
- replace string `"None"` values with actual missing values;
- introduce stable document and chunk IDs;
- add corpus manifests, hashes, and index versions;
- remove destructive whole-collection rebuilds where practical;
- decide later whether the deployed prototype should continue using JSON or use a hosted/vector database.

These corpus improvements are valuable, but they should not block the first deterministic assessment demonstration.

### Step 6: Switch the primary experience

- Make the case dashboard and assessment wizard the default entry point after the reference scenarios pass.
- Retain chat as “Explain this assessment.”
- Keep the legacy application accessible for comparison during the portfolio demonstration, then archive it after v2 is stable.

## 10. First three milestones

Complexity estimates assume one developer familiar with the current repository. They are implementation estimates, not estimates for independent legal validation of every rule.

### Milestone 1 — Domain foundation and persistent cases

**Goal:** Create and reopen a structured assessment case without running legal rules.

**Deliverables:**

- typed v2 fact schema and validation;
- finding and assessment-run models;
- SQLite schema and repositories;
- case create/list/open/archive workflow;
- questionnaire registry format;
- fact editing, tri-state handling, and change events;
- unit tests for validation and persistence.

**Demonstration:** Create a recruitment-system case, answer basic questions, restart the app, and reopen the same normalized facts.

**Estimated complexity:** Medium — approximately 4–6 focused developer days.

**Exit criteria:** Facts survive application restart; invalid values cannot be saved; a case displays schema version and modification history.

### Milestone 2 — Dynamic questionnaire and deterministic classification

**Goal:** Produce traceable EU AI Act scope, role, prohibited-practice, and high-risk findings without RAG or LLM dependence.

**Deliverables:**

- questionnaire sections and deterministic `show_if` behavior;
- rule registry and assessment orchestrator;
- scope and exclusion rules;
- four independent role rule groups;
- Article 5 screening rules;
- Article 6(1), Article 6(2), and Article 6(3) rules;
- information-gap generation;
- rule traces, legal anchors, and ruleset versioning;
- reference fixtures and rule tests.

**Demonstration:** Run the four reference scenarios and show why each conclusion was reached, which facts were used, and which facts remain unknown.

**Estimated complexity:** High — approximately 8–12 focused developer days.

**Exit criteria:** Re-running the same facts and ruleset produces identical findings; all material rules have positive, negative, and unknown tests; no LLM call is required for classification.

### Milestone 3 — Evidence-backed report and assessment-first Streamlit UI

**Goal:** Connect deterministic findings to the existing legal corpus and deliver the complete portfolio workflow.

**Deliverables:**

- reusable `LegalRetriever` adapter over the current vector store;
- metadata-filtered evidence queries derived from legal anchors;
- evidence snapshots attached to assessment runs;
- standardized report builder and Markdown template;
- Results, Evidence, and Report Streamlit pages;
- report download and stale-result warning after fact changes;
- optional “Explain this assessment” chat constrained to saved findings and evidence;
- end-to-end tests for the reference scenarios.

**Demonstration:** Complete a case from questionnaire to downloadable report, then open a finding to inspect its facts, rule trace, and retrieved EU AI Act provisions.

**Estimated complexity:** High — approximately 8–12 focused developer days.

**Exit criteria:** Every material report conclusion maps to a finding; every positive or potential finding shows legal basis and retrieved evidence or an explicit evidence warning; changing a fact does not silently overwrite the previous run.

### Overall prototype estimate

The three milestones total approximately 20–30 focused developer days. A portfolio-ready thin slice can be shown earlier by implementing one reference scenario through all three layers, but the milestone exit criteria should still be completed before describing the system as an EU AI Act assessment prototype.

## 11. Standard report outline

The first report template should contain:

1. Case and assessment metadata.
2. Executive summary.
3. Facts and explicit assumptions.
4. EU AI Act scope finding.
5. Organization role findings.
6. Prohibited-practice screening.
7. High-risk classification.
8. Preliminary obligation groups.
9. Missing information and legal-review items.
10. Legal basis and retrieved evidence.
11. Methodology, ruleset version, corpus version, and disclaimer.

The report builder should assemble this structure deterministically. An LLM may improve explanatory prose, but the stored structured findings, statuses, citations, and information gaps remain authoritative within the prototype.

## 12. Implementation guardrails

- Do not let an LLM write a formal finding directly.
- Do not treat a missing answer as `no`.
- Do not collapse multiple organization roles into one value.
- Do not use the vector store as a transactional case database.
- Do not regenerate a previous assessment run when facts or rules change; create a new run.
- Do not claim GDPR or Data Act applicability in the EU AI Act-only MVP.
- Do not block v2 case and rule development on a complete corpus re-index.
